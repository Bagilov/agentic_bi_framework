# Автоскрины: как устроен конвейер скриншотов (`shots/`)

Документ описывает процесс автоматической съёмки иллюстраций (скриншотов) для
статей, отчётов и документации: зачем он нужен, из чего состоит, как его
запускать и как проверить, что картинка не устарела.

## 1. Проблема, которую решает модуль

До появления `shots/` каждая иллюстрация жила в одноразовом скрипте: свой список
флагов Chrome, своя HTML-«карточка», свой кроп через PIL. Из-за этого:

* **непонятно, что породило картинку** — по имени файла не видно ни источника,
  ни параметров рендера;
* **дублирование** — обёртка терминала, вызов headless-Chrome и нарезка PNG были
  скопированы в нескольких скриптах (это подтвердила инвентаризация: см. §7);
* **нет проверки на устаревание** — если прогон изменился, старая картинка
  остаётся в статье, и никто этого не замечает;
* **неповторяемость** — «вроде бы те же флаги», но результат отличается.

`shots/` делает набор иллюстраций **объектом первого класса**: есть *план*
(что снимать и с какими параметрами), *рендерер* (один вызов браузера) и
*манифест* (размеры, хэши, параметры). Набор воспроизводим и проверяем.

## 2. Общая схема процесса

```
plan (TOML/JSON)                  источник: HTML-файл или текст консоли
      │                                        │
      │   FigureSpec(name, kind, source,       │
      │              width, height, scale…)    │
      ▼                                        ▼
┌─────────────────────┐   kind=terminal   ┌──────────────────────┐
│  shots_build        │──────────────────▶│ shots_terminal       │
│  (оркестратор)      │                   │ текст → HTML-карточка│
│                     │   kind=html       │ (перенос и высота —  │
│                     │──────────────────▶│  в Python)           │
└─────────┬───────────┘                   └──────────────────────┘
          │                                        │
          ▼                                        ▼
┌─────────────────────┐                   ┌──────────────────────┐
│  shots_render       │◀──────────────────│ HTML + точный размер │
│  headless Chromium  │                   └──────────────────────┘
│  (единственный      │
│   список флагов)    │
└─────────┬───────────┘
          ▼
   out/<name>.png  +  manifest.json (sha256, bytes, параметры)
          │
          ▼
   agentic-bi-shots verify  →  набор не изменился?
```

Ключевая идея: **картинку порождает только `shots_render`, а что именно
рисовать — решает план.** Никакой логики в одноразовых скриптах не остаётся.

## 3. Из чего состоит модуль

| Модуль | Ответственность |
|---|---|
| `shots/shots_types.py` | типы плана: `FigureSpec`, `ShotPlan`; валидация всех полей |
| `shots/shots_render.py` | единственный вызов headless Chromium; все флаги здесь |
| `shots/shots_terminal.py` | текст консоли → детерминированная терминальная карточка |
| `shots/shots_manifest.py` | статусы, размеры, sha256, проверка дрейфа |
| `shots/shots_store.py` | детерминированная запись/чтение `manifest.json` |
| `shots/shots_build.py` | оркестратор: пройти план, отрисовать, посчитать хэши |
| `shots/shots_cli.py` | CLI `agentic-bi-shots` (`build` / `verify`) |

Размер каждого файла — в пределах 25–300 строк; браузер, обёртка терминала и
манифест разделены по ответственности.

### Два вида фигур

* **`html`** — источник это HTML-файл: клон отчёта (`web_report`), страница
  board guide, рукописная карточка. Рендерится «как есть», viewport берётся из
  плана.
* **`terminal`** — источник это обычный текст (захваченный вывод CLI). Обёртка
  в терминальную карточку происходит **в Python, а не в браузере**: перенос
  строк и высота карточки детерминированы, и ни одна строка не обрезается.
  Размер viewport подстраивается под карточку, поэтому PNG — это ровно карточка,
  без пустых полей вокруг. Карточка короче 144 px не бывает: это минимум окна
  headless-Chromium (§7), и слишком короткая карточка добивается до него фоном.

Отдельного вида для графики не нужно: **`<canvas>` — это обычная `html`-фигура.**
Браузер рисует канвас до снимка, поэтому диаграмма и график снимаются тем же
планом. Рисование, запущенное по таймеру (`setTimeout`/`requestAnimationFrame`),
попадает в PNG, если успевает сработать в пределах `settle_ms` — виртуальное
время не «спится», а перематывается вперёд (§7). Пример —
`examples/shots/sample-chart.html` и фигура `canvas-chart` в `examples/figures.toml`.

## 4. Формат плана

План — это TOML или JSON. `base_dir` разрешается **относительно файла плана**,
поэтому набор «план + источники» переносится целиком и не зависит от того, из
какого каталога его запустили.

```toml
# examples/figures.toml
base_dir = "shots"          # источники лежат здесь

[defaults]                  # применяется ко всем, если фигура не переопределила
scale = 2.0                 # device scale factor
settle_ms = 300             # virtual time budget, мс

[[figures]]
name = "terminal-card"
kind = "terminal"
source = "sample-run.txt"   # текст захваченного прогона
title = "quality gates"     # подпись в заголовке карточки
columns = 88                # ширина переноса (максимум 96)
point = 13                  # кегль

[[figures]]
name = "html-card"
kind = "html"
source = "sample-card.html"
width = 600                 # viewport, CSS-пиксели
height = 240

[[figures]]
name = "canvas-chart"       # <canvas> — та же html-фигура
kind = "html"
source = "sample-chart.html"
width = 360
height = 180
settle_ms = 500             # таймер рисования успевает сработать
```

Поля `FigureSpec`: `name`, `kind`, `source` (обязательные); `width`, `height`,
`scale`, `settle_ms`, `columns`, `point`, `title`, `out`. Неизвестный ключ —
ошибка (опечатка не проходит молча), значение вне диапазона — ошибка с именем
поля.

План — пользовательский ввод, поэтому он валидируется на границе, а не падает
трейсбеком:

* файл читается только с расширением `.toml` или `.json`; другой формат —
  `plan '…': unsupported format`;
* отсутствующий файл — `plan '…': file not found`; битый JSON/TOML — сообщение с
  файлом, строкой и колонкой;
* `base_dir` обязан быть строкой, `defaults` — таблицей; неизвестный ключ в
  `defaults` репортится отдельно (`unknown key(s) in 'defaults'`), чтобы опечатка
  не приписывалась каждой фигуре;
* `name`, `source`, `title`, `out` обязаны быть строками: `name = 42` больше не
  превращается молча в `"42"`; числовые поля (`width`, `height`, `columns`,
  `point`, `settle_ms`) — целые (`true` и `10.5` отклоняются), `scale` — конечное
  положительное число;
* сообщение называет файл плана и конкретную фигуру: `plan 'figures.toml':
  figure 'run': 'source' is required` (или `figures[2]`, если имя не задано) —
  в плане из десятка фигур не приходится угадывать, какая сломана.

План — это данные, и `out` пишется внутрь `--out-dir`. Поэтому `out` с
каталогом, абсолютным путём или `..`, как и `name` с разделителем пути,
отклоняются: иначе план мог бы писать за пределы выходного каталога. Ошибка, а
не «тихая» санитизация — так опечатку видно сразу.

Имена фигур уникальны: две фигуры с `name = "a"` отклоняются с
`plan 'figures.toml': duplicate figure name(s) ['a']` и кодом выхода 2. Иначе
`--only a` собирал бы обе, `verify --plan` сопоставлял бы по имени и охват был
бы неоднозначным, а в манифесте стояли бы две неразличимые записи. Дубликат
`out` отклоняется так же.

## 5. Запуск

```bash
# собрать набор из плана
agentic-bi-shots --plan examples/figures.toml --out-dir output_files/figures

# то же самое, явной подкомандой; можно ограничить набор
agentic-bi-shots build --plan examples/figures.toml --only terminal-card

# проверить, что набор не устарел (файлы на месте и хэши совпадают)
agentic-bi-shots verify --manifest output_files/figures/manifest.json

# та же проверка плюс сверка с планом: в манифесте есть все фигуры плана?
agentic-bi-shots verify --manifest output_files/figures/manifest.json \
    --plan examples/figures.toml
```

Коды выхода: `0` — все запрошенные фигуры сделаны (или набор `verify` не поехал);
`1` — запрошенная фигура не сделана (упала или пропущена) либо набор разошёлся с
манифестом; `2` — плохой план/манифест или нечитаемый вход.

Сводка `build` — три строки. Путь под текущим каталогом печатается
относительным, каталог вне его — абсолютным (иначе получалось
`../../../../../var/folders/…`). Имя манифеста задаётся `--manifest-name`
(по умолчанию `manifest.json`), и сводка показывает реальное имя:

```text
figures: 2 built, 1 skipped, 0 failed
out: output_files/figures
manifest: output_files/figures/manifest.json
```

Предупреждения (`warning:`) и ошибки (`error:`) идут только в stderr и не
смешиваются со сводкой. `verify` печатает `figures: N checked, M problem(s)` и
строку `manifest: …`, а каждое расхождение — строкой `DRIFT …` в stderr.

Если браузера нет, прогон не падает: каждая фигура получает статус `skipped` с
причиной, сводка это показывает, а в stderr выводится одна строка
`warning: skipped N figure(s) […]: no Chromium browser found …` и итоговая
`error:`. Код выхода — `1`: запрошенные фигуры не сделаны.

### Пример с реальным прогоном (гейты качества)

Источник — не выдуманные строки, а настоящий вывод:

```text
$ ./.venv/bin/python -m pytest
1694 passed, 4 skipped in 39.35s
$ ruff check .
All checks passed!
$ ruff format --check .
340 files already formatted
$ mypy src
Success: no issues found in 185 source files
$ ./.venv/bin/python -m pytest -q --cov=agentic_bi --cov-report=
Required test coverage of 72.0% reached. Total coverage: 79.51%
```

План для этой карточки:

```toml
[[figures]]
name = "pytest-ruff-mypy"
kind = "terminal"
source = "gates_final.txt"
title = "agentic_bi_framework — гейты"
columns = 86
point = 13
```

Результат: `manifest.json` фиксирует размер `712×238` CSS-пикселей (при
`scale=2.0` это PNG `1424×476`) и sha256 картинки. Число CSS-пикселей совпадает
с прежним способом съёмки (`render_terminal.py`), то есть результат
воспроизводим, но теперь не скриптом, а планом.

## 6. Манифест и проверка дрейфа

`manifest.json` — это запись о прогоне. Формат стабилен и **детерминирован**: у
ключа фиксированный порядок, фигуры идут в порядке плана, время не пишется,
пути сведены к именам. Два прогона одного плана дают побайтово одинаковый файл,
поэтому манифест можно диффать и кэшировать.

```json
{
  "browser": "Google Chrome",
  "generated": "",
  "plan": "figures.toml",
  "figures": [
    {
      "name": "pytest-ruff-mypy",
      "kind": "terminal",
      "status": "ok",
      "reason": "",
      "source": "gates_final.txt",
      "png": "pytest-ruff-mypy.png",
      "width": 712, "height": 238, "scale": 2.0,
      "sha256": "238409d7…", "bytes": 66172
    }
  ]
}
```

Что именно делает его детерминированным:

* `generated` по умолчанию пустая строка. Время прогона — единственное, что
  меняется между двумя одинаковыми сборками; библиотечный вызов может передать
  его явно (`write_manifest(..., generated=…)`), CLI этого не делает;
* `browser` — только имя исполняемого файла (`Google Chrome`), не абсолютный
  путь установки; `plan` — только имя файла плана;
* `png` — имя файла относительно каталога манифеста, `source` — имя исходника;
  абсолютных путей в манифесте нет;
* `status` — `ok`, `skipped` или `failed`; у `ok` заполнены `width`/`height`
  (в CSS-пикселях), `scale`, `sha256` и `bytes` (размер PNG на диске), у
  остальных `png`/`sha256`/`bytes` пустые или нулевые, а `reason` объясняет
  причину.

`agentic-bi-shots verify` пересчитывает sha256 каждого файла и сравнивает с
записью. Относительные имена разрешаются от каталога манифеста (переопределяется
`--root`), поэтому набор можно перенести целиком. Любое расхождение —
`DRIFT <figure>: hash mismatch …` и код выхода 1. Записи со статусом
`skipped`/`failed` репортятся как `DRIFT <figure>: not built (status: reason)`:
манифест помнит, что фигуру просили, но не сделали. Это ловит три типовые беды:
картинку правили руками, прогон разошёлся с репозиторием, и фигура так и не
появилась.

Граница проверки: по умолчанию `verify` отвечает за **записанный набор** — что
каждый упомянутый файл на месте и не изменён. Он не сверяет набор с планом,
поэтому `build --no-strict` (или `--only`) может записать в манифест меньше
фигур, чем в плане, и такому манифесту `verify` не возразит. Чтобы закрыть этот
случай, есть `--plan`: тогда каждая фигура плана, которой нет в манифесте,
репортится как `DRIFT <name>: in the plan but not in the manifest (N of M figures
built)` с кодом выхода 1:

```bash
agentic-bi-shots verify --manifest output_files/figures/manifest.json \
    --plan examples/figures.toml
```

## 7. Как это устроено внутри (и почему именно так)

Несколько решений приняты по результатам замеров, а не «на глаз»:

* **Процесс опрашивают, а не ждут его завершения.** Chrome на этой сборке пишет
  PNG меньше чем за секунду (замер: три рендера подряд — 1.08 / 0.87 / 0.95 с),
  но **не всегда завершается сам**: с `--user-data-dir` он не выходит вовсе, а
  его дочерний crashpad-процесс держит унаследованный stdout/stderr, из-за чего
  чтение пайпа до EOF тоже блокируется даже после появления файла. Ожидание
  `exit` вешало любой рендер (набор тестов зависал на 81 с), поэтому
  `shots_render` опрашивает файл: размер должен совпасть в трёх замерах подряд
  **и** файл должен быть целым PNG. Целостность проверяется по сигнатуре и
  завершающему чанку IEND — одного стабильного размера мало, браузер может
  задержаться между порциями записи, и в манифест попал бы хэш обрезанной
  картинки. После этого набор тестов идёт ~3 с.
* **Неудачная фигура не оставляет старый PNG.** Если фигура упала до рендера
  (нет исходника, `--no-strict`) или рендер оборвался, прошлогодний
  `out/<name>.png` удаляется: иначе любой сборщик, забирающий `out/*.png`,
  опубликовал бы картинку, которой нет в манифесте. Причина попадает в манифест
  без путей к каталогам прогона, поэтому две сборки одного плана в разные
  каталоги дают побайтово одинаковый манифест.
* **Одноразовый `--user-data-dir` на каждый рендер.** Он нужен не ради
  корректности одного прогона, а чтобы рендер **не трогал реальный профиль**
  пользователя. Рядом — `--no-first-run` и `--no-default-browser-check`: с
  новым профилем без них браузер встаёт на первичную настройку и рендер не
  возвращается.
* **Обёртка терминала в Python.** Высота карточки считается по числу строк и
  кеглю, а не измеряется в браузере, поэтому картинка не «плавает» и не
  обрезается. Перенос считает **ширину в знакоместах**, а не число кодпоинтов:
  иероглиф занимает две клетки, комбинирующий знак — ноль. Иначе строка из 88
  иероглифов вылезала за карточку и обрезалась.
* **Хайлайт без вложенности.** Маркеры применяются одним проходом, самые
  длинные первыми: иначе `passed` внутри `All checks passed!` вложил бы `<span>`
  в `<span>`.
* **Окно поднимается до минимума браузера.** Headless Chromium не размечает
  окно ниже **144 CSS-пикселей**: замерено, что при меньшей высоте он подставляет
  клампнутый layout-viewport, но всё равно сохраняет PNG запрошенной высоты —
  нижняя часть страницы молча теряется. Поэтому карточка, которая «хотела» быть
  короче, добивается до этого минимума своим же фоном (лишняя полоса невидима),
  а не обрезается; высота окна любой фигуры проходит через `window_height()`
  (`shots_render.py`). Именно этот порог терял тело коротких терминальных
  карточек: карточка из двух строк просила ~121 px и отдавала PNG ровно с
  заголовком. Покрыто тестом `test_short_terminal_card_keeps_its_body_in_the_png`.
* **Виртуальное время перематывается, а не ждётся.** `settle_ms` — это бюджет
  `--virtual-time-budget`: страница «проживает» указанный интервал мгновенно, а
  не спит его. Замер: таймер на 5000 мс при бюджете 500 мс не срабатывает, а сам
  рендер занимает ~0.85 с, то есть бюджет не удлиняет прогон. Поэтому канвас,
  который дорисовывается по `setTimeout`, попадает в PNG только если таймер
  запланирован внутри `settle_ms`; для графики с отложенной отрисовкой бюджет
  увеличивают. Покрыто тестом
  `test_canvas_draw_scheduled_within_settle_ms_is_captured`.
* **Временный HTML-файл не течёт дескрипторами.** `render_html_string` пишет
  источник через `mkstemp`, а он возвращает открытый дескриптор; если его не
  закрыть, каждая отрисованная строка теряет по одному fd, и набор из многих
  терминальных карточек исчерпывает лимит. Дескриптор закрывается сразу после
  `mkstemp`. Покрыто тестом
  `test_render_html_string_does_not_leak_file_descriptors`.
* **Манифест читается как входные данные.** Битый или обрезанный `manifest.json`
  (нет поля, фигура не словарь, `figures` не список, неизвестный `status`,
  значение не приводится к типу) даёт `ValueError` с именем файла и код выхода
  `2`, а не `KeyError`/`TypeError` трейсбеком: `verify` — команда про
  пользовательский ввод, и непонятный манифест это «плохой вход», а не сбой
  фреймворка (`shots_store.read_manifest`, `RenderRecord.from_dict`).
* **Два прогона дают один манифест.** Время, абсолютные пути браузера/плана/PNG и
  порядок словаря убраны из содержимого (§6), поэтому сборка воспроизводима
  побайтово и её можно диффать. Покрыто тестом
  `test_two_runs_write_identical_manifest_bytes`.
* **Нет браузера — это пропуск, а не падение.** `build` один раз ищет Chromium;
  если его нет, каждая фигура получает `status: skipped` с причиной, прогон
  завершается, а код выхода `1` и строка `error:` в stderr объясняют, что
  запрошенные фигуры не сделаны. Одна плохая фигура (нет исходника, пустой или не
  UTF-8 текст консоли) — `failed` с причиной, остальные всё равно собираются.
  Покрыто `tests/test_shots_resilience.py`.
* **`verify` проверяет набор, а не план** — но это можно включить. По умолчанию
  он гарантирует, что записанные файлы на месте и не изменены, а записи
  `skipped`/`failed` репортятся как `not built`; с `--plan` он дополнительно
  ловит фигуру, которую план просит, а манифест не содержит
  (`--only`/`--no-strict`), и это тоже `DRIFT` с кодом 1 (см. §6).
* **План не может писать вне выходного каталога.** `out` и `name` проверяются на
  каталог, абсолютный путь и `..` (§4); это защита от опечатки/подмены плана, а
  не от вредоносного сценария.

## 8. Что было в проекте до этого (инвентаризация)

Инвентаризация `blog_media/` показала дублирование механизмов, которое `shots/`
закрывает:

| Механизм | Где дублировался (до) |
|---|---|
| вызов headless Chrome + список флагов | `other/article-agentic-bi/render_terminal.py`, `dumpui.ps1`, `capture*.ps1`, `views*.ps1` |
| терминальный HTML-«card» + перенос строк | `render_terminal.py` (перенос в Python), `rendercap.ps1` |
| кроп/подгонка PNG | `crop_page.py`, `page_crop.py`, `density.py`, `analyze_shot.py` |

Часть кадров снималась **вручную в гостевой Windows-сессии** (Power BI Desktop):
их автоматизировать нельзя, потому что нет рабочего стола в служебной
WinRM-сессии, и готовность борда ждут по дереву доступности (~38 с). Эти кадры
`shots/` не заменяет — он покрывает **детерминированную часть**: браузерные
рендеры и терминальные карточки, которые снимаются на macOS без виртуальной
машины.

## 9. Что остаётся ручным

* Кадры из живой сессии Power BI Desktop (борд, Model view) — только гостевая
  интерактивная сессия; готовность детектится по UI Automation.
* Снимок может «приехать» от версии Chrome (метрики шрифта), поэтому sha256
  привязан к ревизии инструмента; при обновлении браузера набор пересобирают и
  манифест обновляют вместе с ним.

## 10. Тесты

Тесты разделены по модулям, чтобы границу «нужен ли браузер» было видно по
имени файла:

* чистая часть, работает всегда:
  * `tests/test_shots.py` — валидация плана (обязательные поля, неизвестный
    ключ, диапазоны, дубли имён вывода, `base_dir` относительно плана, фильтр
    `--only`, запрет `out`/`name` за пределами выходного каталога), обёртка
    терминала (перенос с сохранением отступа, CJK/комбинирующие знаки,
    экранирование HTML, хайлайт без вложенности, ширина карточки по `columns`,
    подъём до минимума окна, ненулевой размер), ошибки сборки;
  * `tests/test_shots_manifest.py` — `sha256`, детект дрейфа, отсутствующий
    файл, чтение обратно, отказ на битом/обрезанном манифесте, сверка с планом;
  * `tests/test_shots_boundary.py` — плохой вход плана и манифеста: нет файла,
    битый JSON/TOML, неверный тип поля, неизвестный `status`, формат плана;
    CLI возвращает `2` и печатает имя файла без трейсбека;
  * `tests/test_shots_determinism.py` — два прогона дают побайтово одинаковый
    манифест; в нём нет абсолютных путей и времени; порядок фигур = порядок
    плана; относительные имена PNG проверяются после переноса каталога;
  * `tests/test_shots_resilience.py` — отсутствие браузера даёт `skipped` с
    причиной и код `1` (stderr объясняет), а не падение; пустой/не-UTF-8
    терминальный исходник — `failed` с причиной, остальные фигуры собираются;
  * `tests/test_shots_cli_output.py` — сводка из трёх строк, относительные пути,
    предупреждения/ошибки отдельно в stderr.
* `tests/test_shots_render.py` — требуют Chromium, иначе `skipif`:
  * детерминированность рендера (одинаковый хэш двух прогонов);
  * тело короткой терминальной карточки реально попадает в PNG;
  * отсутствие утечки дескрипторов при строковом рендере;
  * канвас: рисунок попадает в снимок, детерминирован, а таймер внутри
    `settle_ms` срабатывает (вне бюджета — нет);
  * сборка набора end-to-end.

На машине без Chromium модуль `test_shots_render.py` целиком пропускается,
поэтому набор остаётся зелёным.

`board_guide` покрыт отдельными модулями: геометрия и имена страниц, рендер
(`test_board_guide_render.py`), устойчивость к битому `Report/Layout`,
hotspots (`test_board_guide_hotspots.py`: клипинг, минимальный размер, порядок
отрисовки, перекрытия и читаемость подписи), пустые состояния
(`test_board_guide_empty_state.py`), граница входа `.pbix`
(`test_board_guide_input.py`), адаптивность и печать
(`test_board_guide_print.py`), вывод CLI (`test_board_guide_cli_output.py`).
