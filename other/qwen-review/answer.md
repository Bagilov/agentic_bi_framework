Приветствую. Как независимый ревьюер, я проанализировал состояние agentic_bi_framework. Проект амбициозный (работа с бинарными форматами и агентная автоматизация — это всегда боль), но текущее состояние кодовой базы выдаёт в нём скорее «прототип, который решили опубликовать», чем зрелую библиотеку.
Ниже подробный разбор по вашим вопросам.
1. Сигнал vs Шум и риск «красного pytest»
Шум (на что можно закрыть глаза на первом этапе):
Длина файлов (>300 строк). Это косметика. Рефакторинг ради рефакторинга сейчас только замусорит git history.
Количество # type: ignore и : Any. Пока нет строгого тайп-чекера в CI, это просто технический долг, а не блокер.
Плоская структура с префиксами. Это архитектурный антипаттерн, но он не ломает рантайм.
Сигнал (Критические проблемы / Блокеры):
Риск pytest vs python -m pytest (КРИТИЧНО). Это не просто «шум», это индикатор фундаментальной проблемы с конфигурацией проекта. Разница в поведении возникает из-за того, как Python манипулирует sys.path. python -m pytest добавляет текущую директорию в sys.path, а голый pytest (запущенный из .venv/bin/) — нет.
Почему это важно: В CI (GitHub Actions, GitLab CI) тесты обычно запускаются через pytest. Ваш пайплайн гарантированно упадёт. Кроме того, это означает, что тесты зависят от неявного состояния окружения, а не от чётких правил импорта.
Решение: Добавить в pyproject.toml секцию [tool.pytest.ini_options] с pythonpath = ["."] или testpaths = ["tests"], либо сделать tests/ полноценным пакетом (добавить __init__.py, хотя для pytest это уже не строго обязательно при правильном конфиге).
Отсутствие CI и Coverage. 67 нетестированных модулей в фреймворке, работающем с бинарными файлами и агентными действиями — это мина замедленного действия. Один коммит может незаметно сломать парсинг .pbix.
Необъявленная зависимость pywinrm. Пользователь, установивший pip install agentic-bi-framework, получит ModuleNotFoundError при первом же вызове соответствующего кода. Это нарушает базовый контракт Python-пакетов.
Отладочный код в проде. test_build.py как console_script, board_fake.py — это загрязнение неймспейса. Пользователь не должен видеть внутреннюю кухню.
2. Архитектурная оценка
Плоский пакет vs Подпакеты:
Текущая структура (12 engine*.py, 10 brand*.py) — это антипаттерн. Префиксы в именах файлов — это попытка эмулировать директории, которая провалилась.
Вердикт: Дробить на подпакеты обязательно. Должны быть agentic_bi/engine/, agentic_bi/brand/, agentic_bi/skeleton/. Файлы должны называться просто core.py, builder.py, а не engine_core.py. Это улучшит навигацию, импорты и позволит в будущем выносить части в отдельные микросервисы/пакеты.
Фасады-реэкспорты (23 × # noqa: F401):
Вердикт: Это плохая практика. Если вы хотите предоставить плоский публичный API (чтобы пользователь писал from agentic_bi import build_report), то в __init__.py обязательно должен быть прописан __all__ = [...]. Иначе IDE будут сходить с ума, а статические анализаторы будут считать эти импорты мусором. Если плоский API не нужен — удалите фасады, заставьте пользователей импортировать из подпакетов.
3. План улучшений (Приоритизированный)
Цель: превратить прототип в надёжную библиотеку с предсказуемым поведением.
Этап 1: Стабилизация фундамента (Stop the Bleeding)
Цель: Сделать так, чтобы тесты работали везде, зависимости были честными, а базовый CI зелёным.
Шаги:
Исправить конфигурацию pytest (добавить pythonpath в pyproject.toml).
Добавить pywinrm в соответствующий extra (например, [project.optional-dependencies] remote = ["pywinrm"]).
Настроить базовый GitHub Actions (lint, test на Win/Mac, coverage).
Подключить pytest-cov, настроить .coveragerc (или tool.coverage), выставлять минимальный порог (например, 60% на старте).
Критерий готовности: pytest и python -m pytest дают идентичный результат. CI проходит на каждом PR. Отчёт coverage генерируется.
Трудоёмкость: 1-2 дня.
Этап 2: Гигиена и Публичный контракт
Цель: Очистить пакет от мусора, сделать API предсказуемым.
Шаги:
Удалить/перенести отладочные модули (board_fake, _engine_oracle, desktop_oracle_guest).
Убрать test_build.py из console_scripts. Если нужен CLI для проверки, сделать нормальный agentic_bi.cli модуль.
Добавить py.typed в src/agentic_bi/.
Пройтись по __init__.py: либо добавить __all__, либо удалить лишние реэкспорты.
Настроить ruff на проверку BLE (blind except) и T20 (print), чтобы начать борьбу с except Exception и принтами.
Критерий готовности: В установленной библиотеке нет тестовых/фейковых модулей. mypy (в базовом режиме) не ругается на отсутствие py.typed.
Трудоёмкость: 2-3 дня.
Этап 3: Архитектурный рефакторинг и Агентность
Цель: Убрать хардкоды, привести структуру в порядок.
Шаги:
Вынести хардкоды (fact_table, kpi_measures) в центральный config.py или constants.py. Сделать их инжектируемыми (передавать через аргументы функций/конструкторы, а в конфигах хранить дефолты).
Рефакторинг плоской структуры: создать подпакеты engine/, brand/, skeleton/, перенести туда файлы, убрав префиксы из имён. Обновить импорты.
Написать тесты для ключевых нетестированных модулей (особенно validate_pbix, rebuild, lineage/).
Критерий готовности: Структура отражает логику домена. Дефолты можно переопределить без патчинга кода. Coverage > 75%.
Трудоёмкость: 1-2 недели (требует аккуратности, чтобы не сломать обратную совместимость, если она уже есть).
Этап 4: Строгость и Кроссплатформенность
Цель: Сделать код надёжным и понятным для внешних контрибьюторов.
Шаги:
Внедрить mypy --strict (или хотя бы --disallow-untyped-defs) в CI.
Разобраться с except Exception: заменить на конкретные исключения или добавить логирование/рейзинг.
Для macOS/Linux сделать graceful degradation: если вызывается Windows-only код, бросать понятное PlatformNotSupportedError с ссылкой на док, а не падать с FileNotFoundError на msmdsrv.exe.
Критерий готовности: Строгий тайп-чекер зелёный. Нет «голых» эксцепшенов.
Трудоёмкость: 2-3 недели (итеративно).
4. Чего не хватает как библиотеке
py.typed: Пустой файл в корне пакета. Без него типы игнорируются у пользователей.
__all__: Обязателен в __init__.py, если используются реэкспорты.
Тайп-чекер: mypy или pyright в pre-commit и CI.
Проверка extras: Использовать tox или nox с матрицей, чтобы проверять, что pip install .[pptx], .[lineage], .[remote] действительно устанавливают нужное и не ломают базу.
Публикация в PyPI: Настроить Trusted Publishers в GitHub Actions. Добавить в pyproject.toml полные метаданные (readme, license, classifiers, keywords). Добавить CHANGELOG.md (можно генерировать через towncrier или git-cliff).
5. Что делать с дефолтами и отладочными модулями
Дефолты (fact_table, kpi_measures):
Зашивать их в board.py, automate.py и т.д. — это антипаттерн (DIGN: Don't Introduce New Globals).
Решение: Создать agentic_bi/config.py (или settings.py). Использовать pydantic или dataclasses для описания конфигурации.
Агентность: Агент должен иметь возможность прочитать текущий конфиг, изменить его или передать свои имена таблиц при вызове функции. Функции должны принимать table_name: str | None = None, и если None, брать из глобального конфига.
Отладочные модули (board_fake.py, _engine_oracle.py, desktop_oracle_guest.py, test_build.py):
Решение: Жёсткое разделение.
Всё, что нужно для тестов — в tests/.
Всё, что нужно для локальной отладки разработчиками — в tools/ или scripts/ (и исключить из сборки пакета через exclude в pyproject.toml).
test_build.py из console_scripts удалить немедленно. Если пользователю нужен способ проверить, что его окружение настроено верно, сделать команду agentic-bi doctor или agentic-bi check-env в полноценном CLI-модуле.
Резюме
Проект решает сложную и полезную задачу, но обёртка (инфраструтура, тесты, упаковка) пока не соответствует уровню заявленного "фреймворка". Начните с Этапа 1 (фикс pytest и CI) — это займёт пару дней, но снимет 80% головной боли при дальнейшей разработке и избавит от стыда при первом же внешнем ревью.
