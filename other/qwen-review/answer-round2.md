1. Security: XSS и HTML-инъекции
Оценка вектора: Критическая (Severity: High/Critical). .pbix — это по сути архив, который пользователь может скачать из интернета. Если дашборд рендерит метки из этого файла без экранирования, это классический Stored/Reflected XSS (в зависимости от того, как открывается отчёт).
Достаточно ли \u003c?
Да, для этого конкретного места это правильный и достаточный фикс.
Когда JSON вставляется внутрь тега <script>, браузер парсит его как JS, а не как HTML. Единственная опасность — это "breakout" через </script>. Замена < на \u003c (и > на \u003e, а также & на \u0026) — это стандартная практика (так делает Django, Flask, Go). Полноценный HTML-санитайз (типа Bleach) здесь не нужен и даже вреден, так как исказит данные (например, если в метке легитимно есть < или >).
Важное уточнение: Если эти же данные потом рендерятся в DOM через innerHTML (на фронтенде), то там потребуется DOM-санитайз. Но на бэкенде, на этапе генерации HTML, достаточно JSON-escaping.
Отсутствие _e() в _detail_rows:
Если эти поля (fields, roles и т.д.) вставляются в обычный HTML (например, в <td>{m.fields}</td>), то экранирование обязательно. Если они уходят только в JSON — достаточно JSON-escaping. Нужно проверить шаблон.
Что ещё попадает без проверки?
Всё, что приходит из .pbix: имена страниц (tabs), названия визуалов, тултипы, названия таблиц и колонок.
Правило:
Если уходит в HTML-разметку -> html.escape() (или твой _e()).
Если уходит в <script> -> JSON-escaping (<, >, &, /).
Регрессионный тест:
Обязателен. Добавь в tests/ тест, который берёт фикстуру с label = "</script><script>alert(1)</script>", прогоняет через рендерер и проверяет два условия:
В выходном HTML нет последовательности </script><script>.
Извлечённый из HTML JSON успешно парсится json.loads() и содержит исходную строку (round-trip).
2. Упаковка и рантайм-пути
work_dir в site-packages:
Критический дефект (P0). В Linux/Docker site-packages часто смонтирован в read-only. Попытка записи уронит приложение с PermissionError.
Фикс: Использовать platformdirs.user_cache_dir("agentic_bi") или tempfile.mkdtemp(prefix="agentic_bi_").
cwd=str(_HERE) в engine_host.py:
Плохая практика. Код не должен зависеть от того, где лежит его исходник. Если скрипт вызывает внешний процесс, cwd должен указывать на изолированную рабочую директорию (тот самый work_dir из tempfile/platformdirs), а не в site-packages.
Temp-спек без удаления:
Это и утечка дискового пространства, и риск коллизий (epoch имеет секундную точность, при параллельных запусках в CI они сольются).
Фикс: Использовать tempfile.NamedTemporaryFile(delete=False, suffix=".json") (чтобы имя было гарантированно уникальным) и обернуть вызов в try...finally, где в finally делать os.unlink(path).
3. WinRM/PowerShell
Оправдана ли эта боль?
Частично. Запуск GUI-приложения (Power BI Desktop) в headless-среде (Session 0) — это ад. Но зачем вам сам Desktop?
Power BI Desktop — это просто обёртка над msmdsrv.exe (движок Analysis Services) и рендерером отчётов. Если ваша цель — только вытащить DataModel (семантическую модель), вам не нужен GUI. Вы можете запускать msmdsrv.exe напрямую, передавая ему путь к файлу модели. Это убьёт 90% необходимости в WinRM, Scheduled Tasks и RunLevel Highest.
Рекомендация: В рамках подготовки к 1.0 исследовать прямой запуск msmdsrv.exe. Если это возможно — выкинуть весь PowerShell-хак.
Валидация входящих значений:
Если PowerShell всё же необходим, никогда не используй склейку строк (f-strings / format) для передачи аргументов.
Правильный путь: Передавать параметры как Base64-закодированный JSON, а внутри PS-скрипта декодировать его. Либо использовать возможности pywinrm для передачи аргументов.
Если склейка неизбежна — жёсткий whitelist через regex. Например, для имени задачи: if not re.match(r'^[a-zA-Z0-9_\-]{1,64}$', task_name): raise ValueError(...).

Ты абсолютно прав: главная ценность фреймворка — парсинг .pbix. .pbix — это просто ZIP-архив с JSON, XML и SQLite внутри. Его не нужно открывать в Desktop, чтобы парсить.
Что тестировать в первую очередь:
Парсеры DataModel и Report/Layout. Это чистый Python, он должен работать на macOS/Linux.
Golden-тесты (Round-trip). Создай директорию tests/golden/ с 5-10 реальными (но обезличенными) .pbix файлами разного размера и сложности.
Тест: parse(pbix) -> to_dict() -> assert == frozen_snapshot.json.
Тест: parse(pbix) -> serialize(new_pbix) -> parse(new_pbix) -> assert dict1 == dict2.
Это гарантирует, что ты не сломаешь формат при рефакторинге.
Граничные случаи: Пустой отчёт, отчёт с битыми связями, отчёт с очень длинными именами колонок, отчёт с кириллицей/спецсимволами.
Покрытие 37% — это нормально для начала. Сфокусируй новые тесты не на "чтобы было много", а на инварианты формата.

Верхние границы зависимостей (>=):
Для библиотеки отсутствие верхних границ — это правильно. Ты не знаешь, в каком окружении тебя будут использовать. Жёсткие верхние границы (<2.0) вызывают dependency hell у пользователей. Оставь как есть.
Lock-файл:
Для библиотеки poetry.lock / uv.lock в git не нужен (и часто вреден, так как фиксирует транзитивные зависимости, которые могут конфликтовать у конечного пользователя).
Но: Lock-файл обязательно нужен для CI/разработки, чтобы тесты прогонялись на детерминированном окружении. Если ты используешь uv или poetry, пусть они генерируют лок для dev-окружения, но в pyproject.toml укажи, что лок не пакуется в wheel.
